# code1/vision 视觉识别算法分析与提速优化建议

日期：2026-05-22  
范围：`code1/vision` 下 PVC、桥梁/直线、颠簸路、IPM 与 Core1 IPC 相关视觉识别代码。

## 1. 现状概览

当前视觉识别链路已经形成了比较清晰的模块边界：

- `pvc_vision.c/h`：处理 94x60 压缩灰度图，使用白色阈值、连通域 flood-fill、几何打分与防抖输出识别 PVC 入口。
- `line_vision.c/h`：同样处理 94x60 图像，先找桥梁暗色连通域，再通过逐行动态阈值提取白线中心点，最小二乘拟合直线并输出横向偏差、角度和桥梁优先结果。
- `bumpy_vision.c/h`：识别颠簸路白色区域、中心线和暗纹，算法链路最长，包括全局/逐行阈值、连通域、行 run 提取、暗纹支撑判断、相位分类和防抖输出。
- `ipm_transform.c/h`：提供 94x60 全像素 IPM 查表，输出物理坐标或距离。
- `vision_ipc_core1.c/h`：按 0 核下发的 `active_target + enable_mask` 决定哪些模块运行，并把结果打包到共享内存。
- `user/main_cm7_1.c`：每帧复制原图、压缩到 94x60，再根据 `VisionIpc_Core1_ShouldRun*()` 顺序运行 PVC、Line、Bumpy，并可渲染调试图和发送 WiFi 图像。

从代码结构看，这套算法的优点是：输入尺寸小、模块相互独立、输出结构完整、有防抖和 IPC 序号/CRC 机制。当前主要性能风险来自：同一帧被多个模块重复全图扫描、重复构建 mask、连通域 flood-fill 最坏情况不可控、颠簸路算法中百分位/浮点计算较多，以及调试渲染/图传和识别算法在同一帧串行执行。

## 2. 热点判断

以下判断来自静态代码分析，最终应以板上 `runtime_profiler` 或 DWT 周期计数复核。

| 模块 | 主要耗时点 | 代码位置线索 | 优化优先级 |
| --- | --- | --- | --- |
| 颠簸路 | 多次 ROI 直方图、百分位计算、逐行阈值、白色连通域、暗纹支撑扫描 | `bumpy_estimate_white_threshold()`、`bumpy_build_white_scan_mask()`、`bumpy_build_supported_dark_mask()`、`bumpy_collect_components()` | P0 |
| 直线/桥梁 | 桥梁暗色连通域全图扫描、逐行 256 桶直方图、白线 mask 构建、`sqrtf/atanf` | `line_detect_dark_bridge()`、`line_build_near_white_mask()`、`line_fit_points()` | P0 |
| PVC | 全图白色连通域、组件排序、浮点打分 | `pvc_collect_components()`、`pvc_filter_candidates()` | P1 |
| 主循环 | 同帧可连续跑多个视觉模块，且随后可能渲染与图传 | `user/main_cm7_1.c` 中 129-156 附近 | P0 |
| IPM | 单点查表很快，距离开方较贵；表占用 Flash 约 22KB | `IPM_GetDistance_mm()` | P2 |

一个关键事实：图像只有 94x60，即 5640 像素。单次线性扫描并不贵，贵的是“同帧多模块重复扫描 + 每行/每区域多次 256 桶百分位 + flood-fill 最坏情况 + 浮点数学函数”。因此提速方向不应先盲目降分辨率，而应先减少重复工作、限制最坏路径、把浮点和全排序替换成轻量整数/Top-K 计算。

## 3. P0：先建立可测量的耗时闭环

当前三个识别模块的 `*_PROFILE_ENABLE` 默认都是 0。建议先做轻量测量，不然优化容易凭感觉。

### 3.1 打开分阶段 profiler

目标：不仅知道一帧总耗时，还知道耗时花在压缩、PVC、Line、Bumpy、渲染、图传哪一段。

建议做法：

- 保留现有 `g_*_vision_cost_profiler`，新增更细粒度的阶段耗时统计，至少包括：
  - `compress_us`
  - `pvc_us`
  - `line_bridge_us`
  - `bumpy_us`
  - `render_us`
  - `wifi_send_us`
- 每个阶段统计 `last / max / avg / over_budget_count`。
- IPC 包中已有 `frame_dt_us` 与 `cost_us`，建议扩展 `cost_us` 的来源：主任务填“本帧总视觉耗时”，模块字段另行保留模块耗时。
- 先采集三种典型场景：空赛道、强反光、元素入口/内部。强反光通常最容易触发连通域数量上升，是 P99 耗时的关键。

验收标准：

- 能打印或上报各阶段 P50/P90/P99。
- 能确认是否存在某个模块单帧超过预算，例如 100fps 下总视觉预算约 10ms，若还要图传和 IPC，识别算法建议控制在 4-6ms 内。

### 3.2 主循环加入预算调度

当前 `main_cm7_1.c` 中如果多个 `ShouldRun*()` 同时为真，同一帧会顺序执行 PVC、Line、Bumpy。建议改成“主任务每帧跑，辅任务降频跑”。

推荐策略：

| active_target | 每帧运行 | 降频运行 | 触发抢占 |
| --- | --- | --- | --- |
| PVC | PVC | Line/Bumpy 每 3-5 帧或关闭 | PVC 检测稳定后，辅任务可暂停 |
| BRIDGE | Line/Bridge | PVC/Bumpy 每 3-5 帧或关闭 | 桥梁置信度高时跳过直线后续计算 |
| BUMPY | Bumpy | PVC/Line 每 4-6 帧或关闭 | 颠簸 phase 进入 INSIDE 后只保留中心线/暗纹必要路径 |

实现建议：

- 增加 `vision_scheduler_t`，维护 `frame_seq`、上帧耗时、当前预算状态。
- 当上一帧总耗时超过阈值，比如 8ms，下一帧只运行 active target。
- 调试渲染和 WiFi 图传降频，比如识别每帧跑，渲染/发送每 2-4 帧一次。
- 如果 `WIFI_CORE1_ASSISTANT` 或 `WIFI_CORE1_CUSTOM_IMAGE` 打开，图传不应挤占识别预算；建议在耗时超限时自动跳过本帧图传。

预期收益：在多任务同时打开时，最坏帧耗时可以从“三个模块叠加”下降为“一个主模块 + 少量辅任务”，对控制侧最有价值的是输出周期更稳定。

## 4. P0：共享预处理，减少重复全图扫描

三个模块都在 94x60 图上重复做阈值、mask 和 ROI 扫描。建议抽出一层共享的轻量预处理，供模块复用。

### 4.1 建立 `vision_frame_features_t`

建议每帧压缩后先计算一次公共特征：

```c
typedef struct {
    const uint8 *gray;
    uint16 global_hist[256];
    uint16 row_sum[60];
    uint8 row_min[60];
    uint8 row_max[60];
    uint8 row_p60[60];
    uint8 row_p75[60];
    uint8 row_p90[60];
    uint8 global_white_threshold;
    uint8 global_dark_threshold;
    uint8 bright_mask[5640];
    uint8 dark_mask[5640];
} vision_frame_features_t;
```

落地时可以先不一次性加完整结构，先共享最有收益的几项：

- 全局 ROI 直方图：颠簸白阈值、暗阈值、Line 白线阈值都可共用或复用部分统计。
- 行级阈值：Line 和 Bumpy 都有逐行阈值逻辑，可统一为近似百分位。
- 白色/暗色 mask：PVC、Bumpy 的白色区域与 Line 的白线可以用不同阈值派生，但不应每个模块都重新扫全图两三遍。

### 4.2 百分位计算降成本

当前 Line 每行清零 256 桶并计算 p70/p92；Bumpy 对 ROI 和每行都做多次百分位。优化方向：

- 把百分位从 float 形式改成整数 rank：例如 p75 用 `rank = total * 75 / 100`，避免 `floorf/ceilf`。
- 对一份 hist 一次扫描同时取多个百分位，如 p60/p75/p90/p95，而不是每个百分位都从 0 扫到 255。
- 对行阈值使用 32 桶或 64 桶近似直方图：灰度右移 2-3 位，阈值误差 4-8 灰度级，对赛道识别通常可接受，速度明显更稳。
- 对相邻行使用阈值平滑或隔行计算：偶数行算阈值，奇数行复用/插值，Line 的中心提取仍逐行做。

预期收益：Bumpy 和 Line 的阈值计算能减少大量 256 桶扫描，P99 耗时更稳定。

## 5. P0：连通域算法替换 flood-fill

PVC、Line 桥梁、Bumpy 都使用栈式 flood-fill。对 5640 像素小图来说可用，但在噪声/反光碎片多时，访问模式不连续、分支多、最坏耗时和 stack 压力都会上升。

### 5.1 改为行程编码 RLE 连通域

推荐将白色/暗色连通域统一改为 Run-Length Connected Components：

1. 每行扫描 mask，得到若干 run：`y, x0, x1, area`。
2. 与上一行 run 判断横向区间是否重叠或距离 <= 1，合并 label。
3. 对每个 label 累计 `area/xmin/xmax/ymin/ymax/sum_x/sum_y/sum_gray`。
4. 扫完后只保留 top-K 候选，不必保存所有组件。

优点：

- 顺序访问内存，缓存友好。
- 不需要 `visited[IMAGE_SIZE]` 和 `stack[IMAGE_SIZE]`。
- 很容易按 ROI 和边界条件提前剪枝。
- 对“长条、整片白色区域”尤其快，正好匹配 PVC、颠簸白面、桥梁暗块。

### 5.2 早期剪枝

当前 PVC 最终要求 `touches_border`，但 `pvc_collect_components()` 仍扫描所有白点。可优化为：

- 第一阶段只从边界附近或 ROI 边缘种子出发找 PVC 候选。
- 对非边界白斑只统计粗略面积，不做完整 flood-fill 特征。
- 如果 active target 是 PVC 且上一帧已有稳定目标，则先搜索上一帧 bbox 扩大区域；找不到再回退全图。

Line 桥梁可优化为：

- 桥梁暗块阈值目前是固定 `gray < 180`，可先按行统计暗点数量；行暗点低于阈值时跳过该行组件搜索。
- 组件面积/宽高不可能达标时提前停止扩展或不入候选。

Bumpy 可优化为：

- 若行扫描 run 已经足够形成中心线，白色大连通域只做低频或局部验证。
- 暗纹检测只在白色支撑区域附近做，不扫完整 94x60。

预期收益：PVC/Bumpy 的连通域部分最坏耗时明显下降，内存访问更线性。

## 6. P0：颠簸路专项优化

`bumpy_vision.c` 是当前最重的视觉模块。建议分三步优化。

### 6.1 阈值估计轻量化

当前 `bumpy_estimate_white_threshold()` 使用 `double sum/sum_sq`、`sqrtf` 和多个百分位；`bumpy_estimate_row_white_threshold()` 又逐行建 hist。建议：

- `double` 改为 `uint32 sum` 和 `uint32 sum_sq`，94x60 灰度平方最大约 366M，32 位足够；若 ROI 后更小更安全。
- 标准差可用查表或直接移除，改成百分位组合：`threshold = max(p85 - 6, p95 - 12, p75 + (p99-p75)/3)`。
- 全局白阈值每 2 帧更新一次，中间帧复用并做 IIR 平滑。
- 行阈值用 32 桶近似，或只对 ROI 下半部分逐行算，上半部分复用全局阈值。

### 6.2 白面/中心线合并提取

当前先做全局白 mask 和连通域，再做逐行 run 扫描，最后合并 mask。建议把逐行 run 作为主干：

- 每行提取白色 run 后，直接累计最大白面候选的 bbox/area/width/center。
- 中心线由 bottom rows 的 run 加权得到，不再依赖全局连通域。
- 只有在 `run_count` 不足或 phase 不确定时，才启用完整连通域作为补充。

这样可将“连通域 + 行扫描”的双路径变成“行扫描主路径 + 连通域兜底路径”。

### 6.3 暗纹检测使用支撑前缀表

`bumpy_build_supported_dark_mask()` 对每个像素检查上下 offset 2-6 是否有白色支撑，分支很多。建议改成：

- 先为每列建立白色纵向前缀或邻域膨胀 mask：`white_above[y][x]`、`white_below[y][x]`。
- 对暗点只需 O(1) 判断上下窗口是否存在白色。
- 只遍历 `BUMPY_ROI_X/Y`，不要扫完整图。
- 如果 `phase` 已经是 APPROACH 且暗纹还不应出现，可以降频检测暗纹。

预期收益：颠簸模块的重复扫描和浮点计算减少，尤其对高帧率更友好。

## 7. P0：直线/桥梁专项优化

### 7.1 桥梁高置信时跳过直线拟合

`line_detect_frame()` 当前先检测桥梁，随后仍构建白线 mask、提取中心点和拟合直线，最后桥梁优先覆盖直线结果。建议改成双阈值策略：

- 如果桥梁 `bridge_confidence >= high_threshold`，例如 0.75，直接跳过直线计算。
- 如果桥梁处于可疑区间，例如 0.56-0.75，再计算直线作为辅助证据。
- 如果桥梁未检出，才完整运行直线检测。

这样不会降低桥梁优先级，还能在上桥前后节省大量白线处理时间。

### 7.2 白线提取改成 run 直出

当前 `line_build_near_white_mask()` 先构建整幅 `white_mask`，`line_extract_center_points()` 再逐行找 run。建议合并为一次逐行处理：

1. 行阈值计算。
2. 直接提取符合宽度的 run。
3. 按上一行中心选择最佳 run。
4. 存入 `points/widths`。

这样可以去掉 `white_mask[LINE_IMAGE_SIZE]` 的写入和第二次逐行扫描。若调试需要 mask，可只在 debug/render 开启时生成。

### 7.3 拟合与角度固定点化

当前直线拟合使用 float，并计算 `sqrtf` 与 `atanf`。建议：

- `rmse` 判断改成比较平方误差，避免 `sqrtf`：保存 `mse_x100` 或 `rmse_sq`。
- `atanf(k)` 改成小角度近似或查表。对 `|yaw| <= 35°`，可用 `atan_lut[k_x100]`。
- 直线拟合的 `sum_y`、`sum_yy` 对固定 ROI 行号可预计算；如果 point_count 变化，可预存前缀表或用整数累加。
- 评分权重改成 Q15/Q10 定点，输出前再转换。

预期收益：Line 模块在无桥梁时减少 mask 扫描；有桥梁时可大幅跳过直线路径。

## 8. P1：PVC 专项优化

PVC 目前最直接，但仍可提速。

### 8.1 只保留 Top-1/Top-K，不全排序

`pvc_collect_components()` 后按面积排序，`pvc_filter_candidates()` 后按分数排序。实际上最后只使用得分最高的候选。建议：

- 连通域遍历时直接维护 `best_area_components[3]` 或 `best_score_component`。
- 过滤时只比较当前最佳分数，不做完整插入排序。
- `PVC_VISION_MAX_COMPONENTS` 仍可保留用于调试统计，但运行路径不必依赖完整数组排序。

### 8.2 利用边界约束缩小搜索

PVC 过滤要求 `touches_border`，可先扫描边界种子：

- 优先从图像左/右/下边界白色 run 入手，寻找连通域。
- 中央孤立白斑可按行计数跳过，不计算完整特征。
- 对上一帧 bbox 扩张区域优先搜索，稳定跟踪时避免全图。

### 8.3 几何估计改为 IPM 主通道

当前 `forward_mm` 和 `lateral_mm` 仍有经验公式，另外补充了 `phy_x_mm/phy_y_mm`。建议：

- 控制侧优先使用 IPM 坐标，经验公式作为 fallback。
- PVC 识别结果输出 `coord_source` 或置信度修正：IPM 有效时 confidence 不变，IPM 无效时降低 confidence。
- 标定 `entry_bottom_y/centroid_x -> physical` 的查表，替代固定 `20mm/row` 和 `8mm/px`。

这项对速度收益小，但对控制稳定性收益大。

## 9. P1：IPM 与数学函数优化

IPM 查表本身足够快，重点是避免不必要的开方和重复结构体返回。

建议：

- 控制/识别阈值比较优先使用 `IPM_GetDistanceSq_mm()`，只有需要显示真实距离时才调用 `IPM_GetDistance_mm()`。
- 高频单点查询可增加宏或 inline：边界已知合法时直接访问表，避免重复越界判断。
- 若 Flash 紧张，可把 `ipm_table[60][94][2]` 压缩为行级 `y_mm[60] + x_scale[60]`，因为当前表中同一行 `y_mm` 基本恒定，`x_mm` 近似线性。速度可能相当，Flash 可从约 22KB 降到几百字节到 1KB 级别。此项需先验证几何误差。

## 10. P1：输出与 IPC 调度优化

### 10.1 不在识别热路径做调试渲染

`main_cm7_1.c` 中识别后立即调用 `render_*_vision_to_image()`。建议：

- 渲染只在 debug 图传开启时执行。
- 渲染频率独立降频，不超过 20-30fps。
- 渲染使用识别输出，不修改识别输入图；当前注释已经提醒渲染不能放在算法前面，这个边界应继续保持。

### 10.2 发布策略按新帧和主目标触发

`VisionIpc_Core1_Update_2ms()` 已经按 frame_id 和 command seq 判断是否发布。建议增加：

- 主目标有新帧时立即发布。
- 辅目标新帧可以合并到下一次主目标发布，减少 cache clean/invalidate 和共享内存写入频率。
- 对 `frame_dt_us/cost_us` 区分模块耗时与总耗时，避免控制侧误判。

## 11. P2：内存与数据表示优化

当前 scratch 使用多个 `uint8 mask[5640]`，内存还能接受，但带宽和清零成本会叠加。可逐步做：

- mask 改为 bitset：5640 字节降为 705 字节。适合保存全局 mask，但逐像素访问会多位运算，需权衡。
- 行级临时 mask 保持 `uint8 row_mask[94]`，避免整图 mask。
- 对 `visited` 使用帧号标记：`uint8 visited_stamp[SIZE] + current_stamp`，可以避免每帧 `memset`，但 stamp 溢出时需要全清。若改 RLE 连通域，这项可不做。
- 分数/阈值统一 Q10/Q15 定点：减少 FPU/软浮点成本，也让 IPC 输出更直接。

## 12. 推荐实施顺序

### 阶段 A：测量与调度，1-2 天

1. 打开或扩展 profiler，记录压缩、三个识别模块、渲染、图传耗时。
2. 主循环加入 active target 调度：主任务每帧，辅任务降频。
3. 识别超预算时跳过辅任务和图传。
4. 调试渲染降频，并可一键关闭。

预期收益：多任务同时开启时帧周期抖动显著下降，P99 耗时下降最明显。

### 阶段 B：Line 和 Bumpy 热点瘦身，3-5 天

1. Line：桥梁高置信直接跳过白线路径。
2. Line：白线 mask 构建与中心 run 提取合并。
3. Bumpy：百分位计算一次扫描取多个值，去掉 `double` 和不必要 `sqrtf`。
4. Bumpy：暗纹支撑判断改为 O(1) 邻域支撑。

预期收益：主任务为桥梁/颠簸时平均耗时下降，极端光照下更稳。

### 阶段 C：连通域 RLE 化，1 周

1. 先实现公共 RLE 连通域工具，支持白/暗 mask。
2. PVC 切换到 RLE Top-1 候选。
3. Bumpy 白面候选改为 run 主路径，完整连通域做兜底。
4. Line 桥梁暗块改为 RLE 暗域候选。

预期收益：全模块最坏耗时可控，scratch 内存减少，代码路径更统一。

### 阶段 D：标定与定点化，持续推进

1. PVC/Line/Bumpy 输出坐标统一以 IPM 或标定表为主。
2. 把高频评分和阈值计算定点化。
3. 用离线回放数据做参数对比，避免现场凭感觉调参。

## 14. 验收指标

建议以实际板上数据验收，而不是只看代码复杂度：

- 单主任务模式下，视觉算法耗时 P90 小于目标帧周期的 50%。若目标 100fps，建议 P90 < 5ms。
- 多任务开启时，P99 不超过单主任务 P99 的 1.5 倍。
- 图传开启/关闭对识别输出周期影响小于 10%。
- 强反光场景下 `component_count` 增加时，耗时不出现数倍尖峰。
- 控制侧收到的 `frame_dt_us` 抖动下降，`stable_detected` 不因偶发超时断崖式闪烁。

## 15. 按单个算法独立优化方案（不考虑代码复用）

本节只讨论“每个算法自己内部怎么改快”，暂不考虑公共预处理、公共连通域工具、统一参数中心等跨模块复用设计。也就是说，即使 PVC、Line、Bumpy 都需要相似的 run 扫描或阈值函数，也允许各自在本文件内实现一份轻量版本，优先追求局部可落地、风险小、便于单独测试。

### 15.1 PVC 入口识别算法

当前流程：

1. 使用固定白色阈值 `PVC_VISION_WHITE_THRESHOLD = 245`。
2. 全图扫描 94x60，遇到白点后做 flood-fill 连通域。
3. 保存最多 `PVC_VISION_MAX_COMPONENTS = 32` 个白色组件。
4. 先按面积排序，再筛选候选，再按分数排序。
5. 取最高分组件输出 bbox、中心点、距离和防抖结果。

主要耗时点：

- `pvc_collect_components()` 全图 flood-fill。
- `pvc_sort_by_area()` 与 `pvc_sort_by_score()` 对最终只取 Top-1 的场景有冗余。
- 反光碎片多时，白色组件数量上升，flood-fill 分支和栈操作会放大耗时。

独立优化建议：

1. **取消全排序，只维护最佳候选**
   - 在 `pvc_filter_candidates()` 中边筛边打分，直接维护 `best_component`。
   - `component_count/candidate_count` 仍保留用于调试统计，但不再对数组做完整排序。
   - 预期收益：小幅提速，代码风险低，是 PVC 最先建议做的改动。

2. **先筛粗特征，再算浮点分数**
   - 当前先 `pvc_score_component()`，再判断面积、宽高、填充率、是否触边。
   - 建议顺序改为：面积/宽高/填充率/触边通过后，再计算 `score`。
   - 很多噪声白斑会被整数条件提前淘汰，减少浮点计算。

3. **边界优先搜索**
   - PVC 候选最终要求 `touches_border`，可先扫描图像四周边界的白色 run。
   - 对边界连通块完整 flood-fill；对不触边的内部白斑只做跳过或轻量标记。
   - 适合 PVC 入口“从画面边缘进入视野”的先验。

4. **上一帧 bbox 局部优先**
   - 如果上一帧稳定看到 PVC，下一帧先搜索 `bbox` 扩大 6-10 像素后的局部区域。
   - 局部找不到再全图搜索。
   - 预期收益：稳定跟踪阶段大幅减少全图扫描。

5. **固定阈值改成低成本自适应阈值**
   - 当前固定 245 在暗光下可能识别不到，在强光下反光增多。
   - 不考虑复用时，可在 PVC 内部只对下半图或边界区域做一个 64 桶直方图，得到 `p90/p95`，阈值取 `max(235, min(250, p95 - 4))`。
   - 阈值每 2-3 帧更新一次，其他帧复用。

6. **距离输出不影响识别热路径**
   - `pvc_copy_best_to_result()` 中 IPM 查表只查一个点，成本很低，可以保留。
   - 经验公式 `20mm/row`、`8mm/px` 对速度不是瓶颈，优先级低于连通域和排序。

PVC 推荐实施顺序：

1. 先改“粗筛后评分 + Top-1 替代排序”。
2. 再加“上一帧 bbox 局部优先”。
3. 最后加“边界优先搜索”和 PVC 内部自适应阈值。

预期效果：

- 正常场景平均耗时小幅下降。
- 反光碎片多时，P99 耗时更稳定。
- 不改变输出结构，控制侧几乎无感。

### 15.2 桥梁暗块识别算法

当前流程：

1. 在 `line_detect_frame()` 中先调用 `line_detect_dark_bridge()`。
2. 对 ROI 内每个像素判断 `gray < LINE_VISION_BRIDGE_DARK_THRESHOLD`。
3. 遇到暗点后使用 `line_flood_dark_component()` 做暗色连通域。
4. 计算面积、bbox、平均灰度、填充率。
5. 用 `line_score_bridge_component()` 打分，超过阈值则认为看到桥梁。

主要耗时点：

- 每帧桥梁检测都会扫大部分图像。
- 暗色 flood-fill 在大面积阴影或噪声下可能变重。
- 目前即使桥梁已经高置信检出，后续仍会继续跑白线识别。

独立优化建议：

1. **桥梁高置信后短路整帧 Line 后续流程**
   - 在 `line_detect_frame()` 中，如果 `bridge_confidence >= 0.75` 或 bbox 面积/宽高明显满足桥梁条件，直接返回桥梁结果。
   - 不再构建白线 mask，不做中心点提取和直线拟合。
   - 这是桥梁场景最直接的提速点。

2. **按行暗点数量做预筛**
   - 在进入 flood-fill 前，先逐行统计暗点数量。
   - 若一行暗点数量小于如 6-8 个，可跳过该行的连通域种子搜索。
   - 若连续多行暗点数量很低，可判定本帧无桥，直接结束。

3. **限制桥梁搜索 ROI**
   - 当前 `y_min` 约为图像高度 3%，几乎扫到顶部。
   - 可按任务阶段限制：远处桥梁只搜上中部，临近桥梁搜中下部。
   - 如果没有阶段信息，至少可跳过最顶部几行天空/远处噪声区域。

4. **连通域扩展加入面积上限**
   - 桥梁暗块过大时可能是阴影、曝光异常或黑场。
   - flood-fill 中如果 area 超过合理上限，例如 ROI 的 60%，可提前标记为异常大暗域，停止细算或降低分数。

5. **暗阈值自适应**
   - 固定 `180` 在强弱光切换下不稳。
   - 桥梁算法内部可维护一个暗阈值：对 ROI 做 32/64 桶直方图，取 `p20 + 10` 或 `p25 - 6`，限制在 120-190。
   - 不需要和 Bumpy 复用，直接在 `line_vision.c` 内实现即可。

桥梁推荐实施顺序：

1. 先做“高置信桥梁短路白线”。
2. 再做“按行暗点数量预筛”。
3. 最后做“暗阈值自适应 + ROI 限制”。

预期效果：

- 上桥/过桥场景耗时下降明显。
- 误把大阴影当桥的概率下降。
- 对直线跟随逻辑没有负面影响，因为桥梁本来就有更高优先级。

### 15.3 直线/白线识别算法

当前流程：

1. `line_build_near_white_mask()` 对每行建立 256 桶直方图。
2. 每行计算 p70、p92、均值，得到动态白色阈值。
3. 写入整图 `white_mask`。
4. `line_extract_center_points()` 再逐行扫描 `white_mask` 找白色 run。
5. 选择与上一行中心最接近的 run，得到中心点序列。
6. `line_fit_points()` 用最小二乘拟合 `x = k*y + b`，计算 RMSE 和 `atanf(k)`。

主要耗时点：

- 行阈值计算与 `white_mask` 写入。
- `white_mask` 构建后又二次扫描。
- `sqrtf` 和 `atanf` 在高频路径上不划算。

独立优化建议：

1. **合并“建 mask”和“找 run”**
   - 不再先生成整图 `white_mask`。
   - 每行算完阈值后，直接在原始 gray 行上找连续白色 run。
   - 找到最佳 run 后立即写入 `points/widths`。
   - 调试显示需要 mask 时，再在 debug 分支生成。

2. **行直方图改为近似桶**
   - 从 256 桶改为 64 桶：`bucket = gray >> 2`。
   - p70/p92 计算在 64 桶上完成，再左移还原阈值。
   - 对白线识别，4 灰度级误差通常可以接受。

3. **隔行更新阈值**
   - 直线连续性强，不必每行都完整算阈值。
   - 偶数行算阈值，奇数行使用上一行阈值或简单均值。
   - 仍然每行找 run，避免中心点数量减少。

4. **用平方误差替代 RMSE**
   - `line_fit_points()` 中 `sqrtf(err_sum / count)` 只用于和阈值比较/评分。
   - 可保留 `mse = err_sum / count`，评分时比较 `mse` 与 `5.5^2`。
   - IPC 若需要显示 RMSE，可低频或最后近似转换。

5. **角度 `atanf` 查表**
   - `k` 限制在 `|yaw| <= 35°`，范围有限。
   - 将 `k*100` 或 `k*128` 映射到小表，输出 `yaw_error_deg_x100`。
   - 或在控制侧直接使用斜率 `k`，减少角度转换。

6. **上一帧中心线预测**
   - 当前第一行 `prev_center` 固定为图像中心。
   - 可保存上一帧稳定线的 bottom/lookup center，下一帧从预测位置开始选 run。
   - 对连续直线跟随，能减少误选反光 run，提高稳定性；速度收益主要来自更早拒绝异常 run。

直线推荐实施顺序：

1. 先合并 mask 和 run 提取。
2. 再将 256 桶行直方图改为 64 桶。
3. 然后去掉 `sqrtf` 和 `atanf` 高频调用。
4. 最后做上一帧预测增强。

预期效果：

- 无桥梁、纯直线跟随时平均耗时下降。
- 对反光导致的白色碎片更稳。
- 输出字段基本不变，只需注意 RMSE/角度的数值尺度兼容。

### 15.4 颠簸路识别算法

当前流程：

1. `bumpy_estimate_white_threshold()` 在 ROI 内统计直方图、均值、方差、p75/p85/p95/p99，得到全局白阈值。
2. 生成 `global_white_mask`。
3. `bumpy_collect_components()` 对白色 mask 做连通域，找大白面候选。
4. `bumpy_build_white_scan_mask()` 逐行估计阈值、补小 gap、提取 run，得到中心线。
5. 合并 `global_white_mask` 和 `scan_white_mask`。
6. `bumpy_estimate_dark_threshold()` 估计暗阈值。
7. `bumpy_build_supported_dark_mask()` 搜暗纹，并要求上下有白色支撑。
8. `bumpy_find_rib_bands()` 按行聚合暗纹，判断 phase/mode。

主要耗时点：

- 白阈值估计使用 `double`、`sqrtf`、多次百分位扫描。
- 白色连通域和逐行 run 是两套白色识别路径，工作重复。
- 暗纹支撑判断对每个像素检查多个 offset，分支多。
- `BUMPY_MAX_COMPONENTS = 96`，反光多时连通域压力高。

独立优化建议：

1. **去掉 `double` 和标准差开方**
   - 将 `sum/sum_sq` 改为整数。
   - 阈值不再依赖 `stddev = sqrtf(variance)`，改为百分位组合：
     - `candidate = max(p85 - 6, p95 - 10, p75 + (p99 - p75) / 3)`
   - 每 2 帧更新一次全局白阈值，中间帧复用平滑值。

2. **百分位一次扫描取多个值**
   - `bumpy_percentile_from_hist()` 当前每个百分位都可能扫描 0-255。
   - 在 Bumpy 内部写一个专用函数，一次循环同时取 p75/p85/p95/p99。
   - 行阈值同理，一次取 p60/p75/p90。

3. **连通域从主路径降级为辅助路径**
   - 颠簸路中心控制主要依赖 run 和 bottom rows。
   - 可先运行 `bumpy_build_white_scan_mask()` 得到 `run_count/centerline`。
   - 如果 `run_count >= 8` 且 bottom rows 足够，则跳过 `bumpy_collect_components()` 或低频运行。
   - 只有入口阶段不明确时，才做完整白面连通域。

4. **限制白色连通域数量**
   - 如果仍运行 `bumpy_collect_components()`，建议 `BUMPY_MAX_COMPONENTS` 从 96 降到 32 或 48。
   - 对颠簸路这种大白面目标，过多小碎片价值不高。
   - 超出上限后只统计噪声计数，不再 flood-fill 细节。

5. **暗纹检测只在中心线/白面附近**
   - 目前 `bumpy_build_supported_dark_mask()` 扫完整图。
   - 可根据中心线 run 的 `xmin/xmax` 扩大 5-8 像素，只在该横向范围检测暗纹。
   - 如果 phase 是 APPROACH 且尚未进入白面内部，暗纹检测可隔帧运行。

6. **暗纹支撑 O(1) 化**
   - 不考虑复用时，可在 Bumpy 内部为每列计算两个数组：
     - `white_above_near[index]`
     - `white_below_near[index]`
   - 暗点判断时直接查这两个数组，不再循环 offset 2-6。

7. **phase 稳定后裁剪路径**
   - `BUMPY_PHASE_INSIDE`：重点保留中心线 run + 暗纹，入口大白面连通域降频。
   - `BUMPY_PHASE_EXIT`：重点看底部 run，暗纹和全局连通域降频。
   - `BUMPY_PHASE_UNCERTAIN`：才全量运行。

Bumpy 推荐实施顺序：

1. 先去掉 `double/sqrtf`，百分位一次扫描取多个值。
2. 再让 run 中心线成为主路径，连通域降级为辅助。
3. 然后限制暗纹检测 ROI 和频率。
4. 最后做 phase 稳定后的路径裁剪。

预期效果：

- 颠簸路是最重模块，收益最大。
- 平均耗时和强反光 P99 都会下降。
- 因为 Bumpy 输出 phase/mode，路径裁剪可按状态逐步验证，风险可控。

### 15.5 IPM 坐标/距离算法

当前流程：

1. `IPM_GetPhysicalCoord()` 对单个 `(img_x,img_y)` 查 `ipm_table[60][94][2]`。
2. 判断是否越界或无效。
3. `IPM_GetDistanceSq_mm()` 查两个点并计算平方距离。
4. `IPM_GetDistance_mm()` 在平方距离基础上调用 `sqrtf`。

主要耗时点：

- 单点查表很快，不是主要瓶颈。
- 高频调用 `IPM_GetDistance_mm()` 的 `sqrtf` 才需要注意。
- 表占 Flash，但对运行速度影响不大。

独立优化建议：

1. **高频路径只用平方距离**
   - 任何阈值判断都改用 `IPM_GetDistanceSq_mm()`。
   - 例如判断是否小于 300mm，直接比较 `dist_sq < 300*300`。

2. **合法坐标快速查表**
   - 在识别模块内部已经 clamp 到合法范围时，可新增 `IPM_GetPhysicalCoordFast()`。
   - 快速版本不做越界检查，只判断 invalid。
   - 注意只在调用方明确保证合法时使用。

3. **距离开方低频化**
   - 如果只是给调试显示真实距离，每 N 帧算一次 `sqrtf`。
   - 控制侧尽量使用 `x_mm/y_mm` 或平方距离。

4. **表压缩作为空间优化，不作为首要提速项**
   - 当前同一行 `y_mm` 基本恒定，`x_mm` 接近线性。
   - 可用 `row_y[60] + row_x0[60] + row_x_step[60]` 近似替代表。
   - 但这会引入几何误差，建议只在 Flash 紧张时做。

IPM 推荐实施顺序：

1. 先检查是否有高频 `IPM_GetDistance_mm()` 调用，有则改平方距离。
2. 再按需增加 fast 查表。
3. 最后考虑表压缩。

预期效果：

- 对当前识别主流程提速有限。
- 能避免未来控制/识别频繁算距离时引入 `sqrtf` 热点。

### 15.6 单算法优化排期建议

如果每个算法独立推进，建议按收益排序：

| 顺序 | 算法 | 先做项 | 原因 |
| --- | --- | --- | --- |
| 1 | Bumpy | 去 `double/sqrtf`、百分位一次扫描、连通域降级 | 当前链路最长，收益最大 |
| 2 | Line/Bridge | 桥梁高置信短路、白线 mask/run 合并、去 `sqrtf/atanf` | 桥梁和直线都是高频控制输入 |
| 3 | PVC | Top-1 替代排序、粗筛后评分、局部 bbox 优先 | 风险低，容易快速落地 |
| 4 | IPM | 平方距离替代开方、fast 查表 | 局部优化，避免后续成为热点 |

单算法验收建议：

- PVC：记录 `component_count/candidate_count/cost_us`，强反光下 P99 不尖峰。
- Bridge：桥梁稳定检出时，Line 模块耗时明显低于未短路版本。
- Line：无桥直线场景下，输出 `lateral_error/yaw/confidence` 与旧版偏差可控，耗时下降。
- Bumpy：不同 phase 下耗时有明显分层，INSIDE/EXIT 不再总是跑全量路径。
- IPM：距离判断逻辑不再调用开方，坐标输出与旧版一致。

## 16. 总结

当前算法不需要立即推倒重写。最推荐的路线是：

1. 先把耗时测准。
2. 用 active target 调度控制同帧计算量。
3. 把 Line/Bumpy 的重复扫描和重浮点先瘦下来。
4. 再用 RLE 连通域统一替换 flood-fill。
5. 最后做坐标标定和定点化。

这条路线风险较小，兼容现有输出结构，也最符合智能车现场调试的节奏：先稳帧率，再稳识别，再提升几何精度。
