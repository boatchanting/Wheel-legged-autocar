## 1. 目标与范围

将 `trials/bridge` 试验田中验证完成的**远近融合检测管线（v13 门控定版）**迁入主工程，替换现有单边桥检测，并接入既有分支选择机制：

```
                 帧首按上一帧门控二选一 (每帧只跑一个引擎)
 gate_bottom=0                 gate_bottom=1                   gate_top=1
┌──────────────┐ 底部白>75%锁存 ┌──────────────┐ 脱出双重门控    ┌──────────────┐
│ 参考检测器    │ ─────────────▶ │ v8 三线透视   │ ─────────────▶ │ 参考检测器    │
│ (远处中线)    │  单帧锁存      │ (桥上中线)    │  连续3帧锁存    │ (脱出线)     │
└──────────────┘                └──────────────┘                └──────────────┘
```

**v13 定版门控（最终版，勿再改）**：

- **`gate_bottom`（进入门控）**：ref 阶段底部行带 [52,59] 左右线段包络内白像素（>200）占比 **>75%**（2026-08-14 从 50% 提到 75%），单帧锁存，次帧起走 v8；
- **`gate_top`（脱出双重门控）**：v8 阶段每帧同时满足两条，连续 **3 帧**（`BF_TOP_T_FRAMES`）锁存，次帧起切回 ref：
  1. 检出脱出线（`v8.has_top`，v11_top_gy 连通域结束线）；
  2. 底部行带 [52,59] 红/蓝左右边界包络白占比 >75%（"进入"的底部全亮门控）——**无左边线（红）回退 x=2、无右边线（蓝）回退 x=W-2**（mode=2 等单边线帧也可评估）；
  - 旧判据"顶部行带 [4,20] 白占比 <25% 连续 2 帧"已废弃：宽桥场景（桥面占满画面、结束线亦是亮线）下永不触发；
- **单向终态**：far→on→exit 一次走完不回头；多桥/二次检测必须在判离后 `bridge_fusion_init` 重启状态机。

**本次"特大更改"的三个层面**：

1. **检测器大改**：1 核桥检测器从 v6 对齐版升级为 v11 对齐版（v7 四态分类器 + 驳回链 + v11 gy 连通域结束线），见 §3 差异审计；
2. **管线大改**：单检测器 → 远近融合三态管线（ref → v8 → ref），新增融合层与参考检测器，门控按 v13 定版；
3. **接入分支选择**：融合状态机的启停/复位挂到既有元素分支机制（`Plan3/Plan4_StartSpecial` → `VisionBridgeTask_Start` → IPC 使能/复位），恢复 1 核检测的 `ShouldRunBridge` 门控（当前是 `if(1)` 调试态）。

**设计约束（已拍板）**：

- **IPC 协议布局零改动**：字段、打包格式、CRC 一律不动；1 核内部切换检测引擎，输出变化全部收敛进既有 mode + 中线 + 结束线传输逻辑；
- **`b2_mode` 单字节位掩码化**：不再外发 v8 线组合枚举（NONE/R/B/M/RB/...，信息量极少、大量"不可取"组合分散其中）。改为**高 4 位 = 检测状态标志，低 3 位 = 正在干活的状态机（融合阶段）**，0 核一个字节同时知道"检测到了什么"和"现在处于哪个阶段（准备进入/桥上/准备脱出）"；仅改语义与注释，字段布局不变；
- **中线链路按 D1 方案 B**：两个检测引擎各自出中线，在 fusion 门控 if 里按 `fusion_res.source` 二选一——桥上阶段走 arbiter（与现状完全一致），ref 阶段用 ref 自己的中线直供；每帧只跑一个引擎，天然无并行；
- **门控全部在 1 核实现**（融合层 gate_bottom/gate_top/top_t_streak），0 核只是使用结果，**不新增任何门控**；
- **0 核脱出沿用原有 y 门控 + 连续校验机制**：结束线 y 只是判据输入，必须经连续校验（衰减累计）才允许脱出，**绝不允许 y 单帧达标直接触发脱出**；
- **ref 引擎耗时问题不处理**（D3 已拍板）。

**不在本次范围**：0 核控制状态机的控制策略调参、其他赛道元素、`bridge_test_images.c` 板端轮播框架（试验田专用）。

## 6. 决策点记录（全部已定案）

### D1 中线链路 —— **定案：方案 B（各引擎各自出中线，门控 if 二选一）**

**用户定案理由**：两个检测各自独立出中线，直接放进 if 的门控里面，也不会并行执行；每个视觉算法给自己负责到底，改动小、更可靠。

**实施方案**：

- **桥上阶段**（`fusion_res.source==BF_SRC_V8`）：`bridge_v2_arbiter_process(&fusion_res.v8, &arb)` → 滤波层——**和现状一模一样**，arbiter 不动；
- **ref 阶段**（准备进入/准备脱出）：直接用 **ref 自己的稳定中线**——就是试验田 PC 渲染里那条青色统一中线：融合层 `bf_center_from_ref` 已把 ref 的 `center_segment` 转成 `fusion_res.center`（x = a·y + b），无需任何额外加工，适配填入 `bridge_v2_arb_t` 后喂滤波层；arbiter 不参与；
- fusion 每帧只跑一个引擎，两条填料路径天然不并行；
- 适配填充时 `source` 字段填阶段号（0/1/2），滤波层"source 切换清窗"机制借此防止 ref 中线与 v8 中线跨阶段混求中值；该值顺理由 `b2_source` 带上线，与 `b2_mode` 低 3 位冗余，纯诊断。

### D3 ref 引擎耗时 —— **定案：不做任何处理**

ref 引擎 avg 9.25ms / max 15.5ms 超 100fps 帧周期（~10ms）导致的远处阶段丢帧问题，**先不处理**：远处/脱出阶段更新率要求低，IPC 发布在独立 2ms 中断不失锁，桥上 v8 阶段（max 5.96ms）无影响。不预留隔帧代码，后续如确有需要再单独立项。

### D2 IPC 扩展幅度 —— **定案：布局零改动**

IPC 布局零改动，只动 `b2_mode` 一个 uint8 的语义——高 4 位检测状态 + 低 3 位融合阶段（准备进入/桥上/准备脱出），`b2_source` 填阶段号（滤波层清窗需要，顺带带出）；门控全在 1 核（v13 定版），0 核不新增门控、脱出维持原有连续校验。

### D4 文件命名 —— **定案：不改名**

v8 内容继续叫 `code1/vision/bridge_detect.c`，`.ewp` 条目不动。
