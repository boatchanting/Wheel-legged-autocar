# 科目三视觉融合惯导方案

> 目标：在现有“惯导打点 + 寻点 + 元素状态机”的基础上，引入视觉作为近距离确认、入口定位、横向纠偏和出口校正手段。
> 核心原则：惯导负责把车带到元素附近，视觉负责把入口/出口定准，元素内部由局部里程、IMU、轮速和现有状态机稳定通过。

---

## 1. 总体判断

当前惯导已经能把小车带到目标点 5~20cm 范围内，这已经足够让视觉进入“近场搜索”状态。视觉不应该从全程导航开始接管，而应该只在惯导预计接近某个项目点时开启。

推荐逻辑：

```text
NavReplay 按点表运行
-> 距离当前特殊点 < 800mm
-> 开启该项目专用视觉检测
-> 视觉确认入口
-> 记录元素入口姿态 entry_pose
-> 进入项目局部状态机
-> 项目内使用视觉 + 局部惯导 + IMU/轮速控制
-> 识别出口或达到固定长度
-> 用固定赛道长度/出口视觉修正 inertial_nav
-> 清除 g_special_action_trigger
-> 回到 NavReplay
```

不要把视觉做成全局主导航。视觉只应该产生“观测”和“事件”，最终是否触发、是否修正惯导，应该由融合层决定。

---

## 2. 不建议完全关闭惯导更新

你提出了两种思路：

1. 项目内关闭惯导更新，出口后按固定长度补偿。
2. 项目内继续维护进入点、方向角和局部距离，出口后修正全局惯导。

推荐第二种。

原因：

- 完全关闭 `InertialNav_Update()` 会让全局状态在多个模块间变得不连续，后续调试难。
- 项目内轮胎打滑、跳跃、颠簸会污染全局惯导，但可以通过“局部里程只用于项目状态机，出口统一修正全局坐标”来规避。
- 现有代码已经在跳跃时冻结 `vx_body/vy_body`，说明“特定动作期间降低惯导可信度”比“彻底关闭惯导”更自然。

推荐实现方式：

```text
全局惯导继续跑
项目状态机不直接相信全局 x/y
项目状态机维护 local_s_mm
出口时根据 entry_pose + fixed_length 修正 inertial_nav.x/y/yaw
```

也就是：

```c
typedef struct {
    float entry_x_mm;
    float entry_y_mm;
    float entry_yaw_deg;
    float local_s_mm;
    float fixed_length_mm;
    uint8_t active;
} ElementOdom_t;
```

`local_s_mm` 可以来自轮速积分，也可以来自 `inertial_nav.x/y` 相对入口点的投影。项目越颠簸，越建议轮速积分加 IMU 状态门限，出口再统一校正。

## 3. 视觉输出不要直接写触发位

当前代码里已经有这些触发变量：

- `vision_detected_three_jump_point`
- `vision_detected_bumpy_point`
- `vision_detected_bridge_point`
- `vision_detected_jump_point`

这些变量可以先保留作为兼容层，但视觉模块不要直接写它们。否则容易出现视觉误识别直接打断状态机的问题。

推荐新增统一视觉事件：

```c
typedef enum {
    VISION_EVT_NONE = 0,
    VISION_EVT_STAGE_UP,
    VISION_EVT_STAGE_DOWN,
    VISION_EVT_BUMP,
    VISION_EVT_BRIDGE,
    VISION_EVT_GRASS,
} VisionEventType_e;

typedef struct {
    VisionEventType_e type;
    float forward_mm;       // 图像查表得到的前向距离
    float lateral_mm;       // 横向偏差，正方向统一约定
    float yaw_error_deg;    // 元素中心线或边线相对车身的角度误差
    float confidence;       // 0.0 ~ 1.0
    uint32_t timestamp_ms;
} VisionEvent_t;
```

融合层做判断：

```text
只有当前 NavReplay 预期项目 == 视觉事件项目，才允许触发
只有距离特殊点 < 800mm，才开启该项目视觉
confidence > 0.60，允许修正距离/角度
confidence > 0.85 且连续 3~5 帧成立，允许触发状态机
项目状态机 active 时，禁止其他项目视觉触发
```

## 4. 96x60 图像的距离方案

你说“距离可以直接打表，不做逆透视”，这个方案可用，并且更适合现在快速落地。

建议至少准备三张表：

```c
// y 行号 -> 前向距离，单位 mm
float vision_row_to_forward_mm[60];

// x 列偏移 -> 横向距离，单位 mm
float vision_col_to_lateral_mm[96];

// 两个点的 dx/dy -> 角度误差，可用 atan2 或查表
float vision_angle_table[...];
```

V1 可以只做 `row_to_forward_mm`：

- 入口线在图像中越靠下，距离越近。
- 通过标定，把白色 PVC 入口线、台阶蓝色边、单边桥黑楔形前缘对应的行号记录成距离。
- 每次识别只输出最可信的目标行号，再查表得到 `forward_mm`。

后续优化再加横向距离和角度。

## 5. 通用状态机

建议所有项目共用这个外层流程：

```text
ELEMENT_IDLE
-> ELEMENT_SEARCH_ENTRY     等视觉确认入口
-> ELEMENT_ENTRY_LOCK       记录 entry_pose，锁定项目初始航向
-> ELEMENT_EXECUTE          项目内部动作执行
-> ELEMENT_SEARCH_EXIT      找出口，或等待固定长度完成
-> ELEMENT_EXIT_CORRECT     修正惯导，交还 NavReplay
```

项目内部控制权优先级：

```text
跳跃/桥/颠簸状态机输出
> 视觉局部横向纠偏
> NavReplay 的路径跟踪输出
> 遥控器普通速度输入
```

也就是说项目激活后，`NavReplay_Process()` 不能继续覆盖 `target_speed_set` 和 `err_degree`。

## 6. 上三级台阶

### 6.1 视觉怎么做

识别目标：

- 入口白色 PVC 边界。
- 中间蓝色台阶在灰度图中通常表现为较暗的横向区域。
- 白-暗-白结构，即白色 PVC/台阶面中夹一个明显暗横条。

96x60 图像建议只看中下部 ROI：

```text
x: 10 ~ 85
y: 20 ~ 58
```

视觉输出：

```text
stage_entry_forward_mm
stage_lateral_mm
stage_yaw_error_deg
confidence
```

V1 检测逻辑：

1. 二值化白色区域，找左右白边线或白色赛道大连通块。
2. 在白色赛道内部找横向暗块，暗块宽度要大于一定阈值。
3. 暗块上下都能找到白色区域，认为是台阶蓝色区域。
4. 取暗块前缘或入口白边线的行号，查表得到距离。
5. 连续 3 帧识别到相似距离，认为入口有效。

不要指望上台阶过程中持续视觉闭环。车身抖动、仰角变化、图像丢失都很明显。视觉主要负责定入口和定出口。

### 6.2 惯导怎么做

入口确认后记录：

```text
entry_x
entry_y
entry_yaw
```

项目内维护：

```text
local_s_mm = 从入口开始沿 entry_yaw 方向累计的局部距离
```

三次跳跃点不要直接靠视觉逐次找。建议靠局部距离触发：

```text
jump1_s = 第一级前缘距离 - lead
jump2_s = 第二级前缘距离 - lead
jump3_s = 第三级前缘距离 - lead
```

现在 `servo_jump.c` 里已经有三级台阶几何和 `STEP_UP_TRIGGER_LEAD_MM`，可以继续沿用，视觉只修正第一个入口。

出口处理：

```text
如果识别到下坡出口白 PVC：
    用视觉出口距离辅助结束
否则：
    local_s_mm >= 固定台阶总长度 + 安全余量时结束
```

退出时修正全局惯导：

```text
inertial_nav = entry_pose 沿 entry_yaw 前进 fixed_stage_up_length
relative_yaw = entry_yaw 或 当前 yaw 低通融合
```

具体坐标正负要使用当前工程里的坐标定义封装成一个函数，不要在多个文件里手写。

### 6.3 控制怎么做

入口前：

- 低速接近。
- 根据视觉 `yaw_error_deg` 修正 `err_degree`。
- 入口距离小于触发阈值后锁定航向。

执行中：

- `target_speed_set` 由台阶状态机接管。
- 三次跳跃用 `jump_trigger_with_type(JUMP_TYPE_STEP_UP)`。
- 跳跃期间冻结或降低惯导速度可信度。
- 每次落地后用 `pitch/gyro` 判断是否稳定，再允许下一跳。

出口：

- 识别到坡道末端或固定长度完成。
- 停短时间或低速平稳恢复。
- 清 `g_special_action_trigger`。

### 6.4 简单方案

视觉只做入口确认：

```text
惯导到 80cm 内
-> 识别蓝色/暗横条入口
-> 修正第一跳距离
-> 后续三跳全部按 local_s_mm
-> 固定长度退出
```

优点：实现简单，抗图像抖动。

缺点：如果入口识别晚了，三跳整体会偏晚。

### 6.5 提速方案

提速优化：

- 在入口前 80cm 就用视觉提前对齐角度，不等到 20cm 才调。
- 第一跳触发点由视觉实时距离决定，后两跳由落地检测 + 局部距离共同决定。
- 每次跳跃后不完全停稳，只要求 pitch/gyro 落入安全窗口就继续。
- 出口识别到下坡末端后立即恢复 `NavReplay`，减少固定等待。

## 7. 下三级台阶

### 7.1 视觉怎么做

识别目标：

- 坡道入口白色 PVC 起始线。
- 坡道两侧白边线。
- 台阶/平台末尾白色出口。

下三级台阶与上三级台阶不同，视觉不需要识别每一级台阶。重点是识别“开始上坡”和“已经离开台阶区”。

V1 检测逻辑：

1. 在近场 ROI 找白色 PVC 大区域。
2. 如果白色区域宽度逐渐变化、边线收敛明显，认为接近坡道。
3. 入口行号查表得到 `stage_down_entry_forward_mm`。
4. 出口用白色 PVC 连续平整区域恢复、横向边界稳定作为判断。

### 7.2 惯导怎么做

入口确认后记录 `entry_pose`，维护 `local_s_mm`。

下台阶过程中全局惯导可信度低：

- 轮胎可能离地。
- 每次落地冲击会让加速度异常。
- 轮速可能短时跳变。

因此项目内只用局部距离和 IMU 状态判断阶段，不直接用全局坐标判断是否到点。

推荐阶段：

```text
上坡段：local_s_mm < ramp_length
平台段：local_s_mm 到达顶部平台
下台阶段：按固定距离/姿态变化依次通过三级
出口段：local_s_mm 到达固定总长或视觉看到出口
```

退出时同样按固定总长度修正全局惯导。

### 7.3 控制怎么做

上坡：

- 中低速。
- 锁航向。
- 底盘姿态保持稳定，不做大动作。

下台阶：

- 不建议完全靠视觉逐级触发。
- 使用 `pitch` 和垂向冲击判断“已经落下一阶”。
- 每次落地后短暂限速，防止连续前翻。
- 可设计独立 `StageDown_Update()`，不要复用上三级跳状态机。

出口：

- 看到末尾白 PVC 或 local_s 到固定长度。
- 恢复正常底盘高度和速度。
- 修正惯导并退出。

### 7.4 简单方案

```text
视觉确认坡道入口
-> 锁航向上坡
-> 按固定距离和 pitch 变化依次下台阶
-> 固定长度退出
```

优点：不依赖台阶过程中图像。

缺点：对速度和姿态参数要求较高。

### 7.5 提速方案

提速优化：

- 坡道入口前提前对齐，不停车。
- 用 pitch 斜率判断已经上坡，动态切换速度。
- 下台阶时用落地冲击检测代替固定等待。
- 出口视觉确认后立即把全局惯导拉回出口点，不等完整固定长度。

## 8. 颠簸路段

### 8.1 视觉怎么做

识别目标：

- 入口白色 PVC。
- 颠簸路肩形成的横向暗/亮条纹。
- 出口白色 PVC 或条纹消失。

V1 检测逻辑：

1. 找白色 PVC 赛道区域。
2. 在赛道区域内统计横向条纹数量。
3. 条纹密度达到阈值，认为是颠簸路段。
4. 入口行号查表得到距离。
5. 出口检测为条纹密度下降，并且白色区域连续稳定。

颠簸过程中图像会抖，视觉不要做主控制，只用于入口和出口。

### 8.2 惯导怎么做

入口确认后记录 `entry_pose`，清零 `local_s_mm`。

项目内：

- `local_s_mm` 用于判断是否达到最短通过距离。
- 如果视觉看到出口，可以提前结束。
- 如果视觉丢失，则固定长度兜底。

颠簸路段可能有两种摆法：

```text
整段 1m+
两个 50cm 段，中间间隔 50cm
```

建议状态机支持“段计数”：

```text
BUMP_SEG_1
BUMP_GAP
BUMP_SEG_2
BUMP_EXIT
```

V1 可以先不分段，按最长固定长度通过。

### 8.3 控制怎么做

沿用现有 `BumpyRoad_Update_1ms()` 的思路：

- 恒定速度。
- `err_degree = 0` 或锁定入口航向。
- 堵转检测：左右轮速小 + pitch 明显异常 + 持续时间满足。
- 堵转后后退、前冲、跳跃。
- 跳跃期间保护惯导速度状态。

视觉只负责：

- 入口触发。
- 出口结束。
- 如果出口没识别到，固定长度兜底。

### 8.4 简单方案

```text
惯导到 80cm 内
-> 视觉确认入口白 PVC/横向条纹
-> 触发 BumpyRoad_Trigger()
-> 恒速 + 堵转检测
-> local_s 超过固定长度退出
```

优点：最容易接到现有代码。

缺点：出口不够精准，可能多跑一小段。

### 8.5 提速方案

提速优化：

- 入口视觉距离用于提前加速，不在入口处停顿。
- 条纹密度用于判断当前处于颠簸段还是中间空段。
- 空段略提速，条纹密集段降速。
- 出口视觉确认后立即退出，不等待固定距离。

## 9. 单边桥

### 9.1 视觉怎么做

识别目标：

- 白色 PVC 赛道左右边界。
- 黑色楔形单边桥。
- 楔形在左侧还是右侧。
- 已经通过了几个楔形。
- PVC 终点。

视觉主线应该是白色 PVC 的中心线，不是黑色楔形。

原因：

- 黑色楔形左右交错，如果追黑色目标，方向会左右摆。
- 小车真正要保持的是沿 PVC 赛道中心前进，同时在经过楔形时做 roll/底盘策略。

V1 检测逻辑：

1. 二值化白色区域，提取 PVC 左右边界。
2. 计算 PVC 中心线，输出 `lateral_mm` 和 `yaw_error_deg`。
3. 在 PVC 内找黑色连通块。
4. 黑色块中心在图像左半区，记为左桥；在右半区，记为右桥。
5. 按 `local_s_mm` 做去重，同一楔形只计数一次。
6. `bridge_count >= 3` 且看到 PVC 终点，退出。

楔形计数建议加防抖：

```text
同一黑色块连续 3 帧出现才计数
两次计数之间 local_s_mm 至少相隔 100~150mm
计数顺序异常时不立即退出，只降低 confidence
```

### 9.2 惯导怎么做

入口确认后记录 `entry_pose`，清零 `local_s_mm`。

项目内：

- 局部距离用于桥计数去重和出口兜底。
- 如果视觉漏掉一个楔形，可按预期间距补一个虚拟计数，但要保守。
- 全局惯导不直接决定是否出桥。

出口：

```text
bridge_count >= 3
并且
看到 PVC 终点距离 < exit_threshold
或 local_s_mm > bridge_fixed_length
```

退出后按桥总长度修正全局惯导。

### 9.3 控制怎么做

入口：

- 视觉确认 PVC 和第一个黑楔形。
- 抬底盘。
- 锁定入口航向。

通过中：

- 方向控制由 PVC 中心线给 `err_degree`。
- 黑色楔形只提供“左/右”和计数，不直接作为路径中心。
- 根据左/右楔形给 `roll_degree` 或底盘侧向补偿。
- 如果视觉短时丢失，保持最近一次中心线和入口航向，盲跑一小段。

出口：

- 计数达到 3。
- 看到 PVC 终点或 local_s 到达总长。
- 降底盘。
- 恢复普通 PID 参数。

### 9.4 简单方案

```text
识别白 PVC + 黑楔形入口
-> 抬底盘
-> 按固定 L-R-L 距离表给 roll 偏置
-> PVC 中心线只做轻微方向修正
-> local_s 到固定长度后降底盘退出
```

优点：实现快，视觉压力小。

缺点：如果实际桥间距变化较大，压桥精度一般。

### 9.5 提速方案

提速优化：

- PVC 中心线实时控制方向，允许更高速度。
- 黑楔形视觉计数实时修正每个 roll 偏置的触发距离。
- 桥间距由视觉测得后动态更新，不完全依赖固定表。
- 出口看到 PVC 终点后提前降底盘，缩短冷却距离。

## 10. 草地路段

### 10.1 视觉怎么做

如果使用 MT9V03X 灰度图，草地识别可靠性不如台阶和单边桥。草地纹理可能受光照影响很大。

V1 不建议把草地视觉作为强触发。建议：

- 惯导点表触发草地。
- 视觉只做辅助确认。
- 轮速下降、速度环输出增大、加速度变化作为主要确认。

视觉可以尝试：

- 白色 PVC 消失或边界纹理变乱。
- 图像局部灰度方差增大。
- 赛道区域不再是稳定白色块。

### 10.2 惯导怎么做

入口由点表或视觉确认后记录 `entry_pose`。

项目内：

- 用 `local_s_mm` 走固定长度。
- 因为草地阻力大，轮速和实际速度可能不一致，需要用 IMU/姿态和速度闭环判断是否卡住。

出口：

- 视觉恢复白色 PVC 或 local_s 到固定长度。
- 修正惯导。

### 10.3 控制怎么做

- 降低速度突变，避免进入草地瞬间冲击。
- 速度环可以适当提高输出上限。
- 如果轮速下降但车体姿态正常，说明阻力增大，不要误判为堵转跳跃。
- 如果长时间速度低且 pitch 异常，再进入脱困逻辑。

### 10.4 简单方案

```text
点表触发草地
-> 固定速度/固定输出上限通过
-> local_s 到固定长度退出
```

### 10.5 提速方案

```text
视觉检测草地边界
-> 提前加大速度环输出能力
-> 出草地看到白 PVC 后立即恢复普通参数
```

## 11. 融合修正方式

入口修正：

```text
惯导预计特殊点坐标：P_map
视觉测得元素相对车体坐标：P_rel
当前航向：yaw

反推车体视觉坐标：
P_car_by_vision = P_map - Rotate(yaw) * P_rel

残差：
dx = P_car_by_vision.x - inertial_nav.x
dy = P_car_by_vision.y - inertial_nav.y

门限通过：
inertial_nav.x += k * dx
inertial_nav.y += k * dy
```

V1 可以不做入口坐标修正，只做触发距离修正：

```text
视觉入口距离 d
local_s_mm = -d
当 local_s_mm >= 0 时进入项目
```

出口修正：

```text
corrected_pose = entry_pose + fixed_length along entry_yaw
inertial_nav.x = corrected_pose.x
inertial_nav.y = corrected_pose.y
inertial_nav.relative_yaw = lowpass(current_yaw, entry_yaw 或视觉出口 yaw)
```

注意：工程里 `x/y/yaw` 的正负方向已经由现有 `NavReplay_Process()` 使用，建议封装一个统一函数：

```c
void NavPose_AdvanceAlongHeading(
    float start_x,
    float start_y,
    float heading_deg,
    float forward_mm,
    float *out_x,
    float *out_y
);
```

不要在各个项目文件里重复写坐标公式。

## 12. 推荐落地顺序

第一阶段：只做能跑方案。

```text
1. 新建视觉事件结构
2. NavReplay 接近特殊点 80cm 内开启对应视觉
3. 上三级台阶：视觉只定入口，local_s 三跳
4. 颠簸：视觉只定入口，固定长度退出
5. 单边桥：视觉定入口，固定 L-R-L 表通过
6. 出口统一按固定长度修正惯导
```

第二阶段：增强稳定性。

```text
1. 每个项目加入出口视觉
2. 所有视觉事件加连续帧确认
3. 加 confidence 和误触发门限
4. 单边桥加入黑楔形计数
5. 下三级台阶独立 StageDown 状态机
```

第三阶段：提速。

```text
1. 单边桥 PVC 中心线视觉闭环
2. 台阶第一跳视觉动态触发
3. 颠簸条纹密度判断分段
4. 出口视觉提前恢复 NavReplay
5. 参数按项目自动切 PID 和速度上限
```

## 15. 最终策略总结

科目三的视觉融合不要追求一开始就“全视觉控制”。最稳的版本是：

```text
惯导负责到项目附近
视觉负责确认入口和出口
项目内用局部里程 + IMU + 轮速 + 现有状态机
退出时统一修正全局惯导
```

各项目优先级：

```text
上三级台阶：视觉定入口，局部惯导触发三跳
下三级台阶：视觉定入口/出口，IMU 判断下台阶
颠簸路段：视觉定首末，堵转检测和恒速通过
单边桥：视觉看 PVC 中心线，黑楔形计数和侧别判断
草地：点表为主，视觉和轮速阻力作为辅助确认
```

这个版本足够先跑通，后续再逐个项目把视觉从“确认入口”升级为“局部闭环提速”。
