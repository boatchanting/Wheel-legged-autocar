## 2. 内存约束（不变的事实）

### 2.1 icf 不可改（用户确认）

```
define symbol cm0plus_sram_reserve = 128K; // (SRAM0/~128KB) -> cm0plus
define symbol cm7_0_sram_reserve   = 512K - cm0plus_sram_reserve; // (SRAM0/384KB) -> cm7_0
// CM7_1 = 768K - 128K - 384K = 256K (SRAM1, 物理硬上限)
```

- CM7_1 SRAM 区域 `[0x2808'0000, 0x280b'ffff]` = 256KB，其中末尾 8KB 为 CSTACK；
- 任何把 CM7_0 分给 CM7_1 的改动都不允许。

### 2.2 瘦身前后账目（IAR map 实测，`iar/Debug_m7_1/List/cyt4bb7_cm_7_1.map`）

| 配置 | ro code | rw code(ITCM) | ro data | rw data(SRAM) | 结果 |
|---|---|---|---|---|---|
| 宏=0（瘦身前基线） | 70,036 | 4,964 | 27,459 | 152,758 | 通过 |
| 宏=0（瘦身后） | 70,036 | 4,964 | 27,459 | 152,758 | 通过，**与基线逐字节一致** |
| 宏=1（瘦身前） | — | — | — | 需求 380,772 | ❌ 溢出 ~124KB |
| **宏=1（瘦身后）** | 76,420 | 4,964 | 27,460 | **255,634** | ✅ **通过，余量 6,510B** |

- TCM 不是瓶颈：ITCM 4,964/16K、DTCM ~7.7/16K，瘦身前后均不变；
- `s_bumpy_pipeline` 实例：124,160B → **95,960B**（0x1'76d8）。

## 4. 被否决的旧方案（留档）

旧规划 §5 的三步方案经源码核查后**未采用**：

1. **旧 A1（分位就地化）**：方向正确，但其附带动作"strong/horiz 用 gx/gy 现算"在代码里**早已完成**——mag2 的唯一用途就是喂分位；
2. **旧 A2（卷积流式化 gxh/gyh，中风险需重新对拍）**：**不必要**。卷积在帧首执行，此时 mag2 的 45,120B 完全空闲，gxh/gyh 直接借用即可，零算法改动、无需重新对拍；
3. **旧 B（bridge_detect 瘦身 30-40KB）**：**不必要**。（若采用叠加方案，省下的内存已足够；且用户要求 bridge 绝对不能动。）

## 5. 实际落地的瘦身方案：纯缓冲时分复用（零算法改动）

核心观察：各工作缓冲的**生命周期互不重叠**，可在 `bumpy_pipeline_t` 内按阶段复用同一块内存。所有改动只落在 `bumpy_pipeline.c/.h`、`bumpy_conv.c/.h` 三个文件，计算语句一条未改 → 对拍结果逐位一致，**无需重新对拍**。

| 手段 | 节省 | 做法 | 生命周期论证 |
|---|---|---|---|
| 分位就地化 | −45,120 | `percentile_q64` 去掉内部 `static uint64_t buf[PIX]` 拷贝，直接对 mag2 就地 quickselect | mag2 分位后不再使用（strong/horiz 本就由 gx/gy 现算），③ memset 复用为 relab |
| gxh/gyh 借 mag2 | −45,120 | `bumpy_conv7` 增加 `scratch` 参数（2×BUMPY_PIX int32），调用方传 `(int32_t*)s->mag2` | 卷积是帧首第一件事，mag2 在卷积返回后才逐像素写入 |
| labels 借 gx | −22,560 | 结构体删 `labels[PIX]`，CCL 标号写 `(int32_t*)s->gx` | gx 在阶段②后不再被读；labels ③④才用 |
| uf 借 gy | −22,564 | `static int32_t uf[PIX+1]` 删除，帧首 `uf = (int32_t*)s->gy` | gy 同样在②后自由；uf 用量 ≤ PIX/2+1（新标号像素可单射到非 horiz 像素）≪ PIX |
| strong 改局部量 | −5,640 | 结构体删 `strong[PIX]`，循环内写完即被同一迭代消费 | `st` 是逐迭代临时值，从不跨迭代/跨阶段读 |

**合计 −140,764B**，宏=1 rw data 从 380,772 → **255,634B**（上限 262,144，余量 6,510B）。

### 零影响保证（可检验判据）

- 改动文件只在 CM7_1 工程的 vision 组；CM7_0/CM0+ 不编译；
- bridge ↔ bumpy_pipeline/bumpy_conv 双向零引用（已 grep 确认）；
- 宏=0 时 `bumpy_pipeline.o`/`bumpy_conv.o` 被链接器整体剥离（map 中段贡献为 0），
  瘦身后宏=0 构建 map 四项总量与基线**逐字节一致**（152,758B rw data 等）；
- `edge_conv7_asm.s`、icf、IPC 契约、0 核、bridge 全部未触碰。

### 注意事项

- `BP_DEBUG_FRAME=1` 的调试打印：strong 计数改为②循环内同步累计；末尾重算的 thr 值读到的
  是 relab 复用后的 mag2（改动前同样不可信，非本次引入）；
- 参考工程（bumpy-road-new，不在本仓）若再次整文件同步，需把这轮 overlay 改动一并带回
  （语义未变，host 对拍仍可通过；`bumpy_conv7` 多了 scratch 参数，host 侧传一个静态数组即可）。

## 7. 附录：已确认的事实（避免反复）

1. icf 不改：CM7_1 = SRAM1 = 256K 硬上限（区域 `[0x2808'0000, 0x280b'ffff]`，末尾 8K CSTACK）；
2. TCM 没炸：ITCM 4.9/16K、DTCM 7.7/16K，均有余量，瘦身不涉及 TCM；
3. 宏=0 时新管线目标文件被链接器整体剥离 —— 这是"宏=0 产物逐字节一致"的机理；
4. 测试图集 `bumpy_test_images`（66KB，Flash）**未迁移**，与本次无关；
5. `ipm_transform` 的 22KB 是 `const`（Flash），不算 RAM；
6. 参考工程 RAM-优化版（MAX_CC 64）已同步到主工程并验证通过；
7. uf 并查集用量上界证明：新标号像素 ⇒ 左邻或上邻非 horiz，可单射到非 horiz 像素，
   故 ≤ PIX/2+1 项，gy 区（PIX 项）容纳无风险。
